Infrastructure — Data Flows & Principles

Data flows

A
Collector ingestCollector → ALB → ECS → RDS
Outbound HTTPS from the customer LAN, HMAC-signed on every request. No inbound firewall change at site.
B
Command dispatchPortal → ECS → Collector → device
Commands are queued in PostgreSQL and delivered on the Collector's long-poll. The result is returned to the portal in under a second, pushed by LISTEN/NOTIFY.
C
Portal (interactive)Browser → Amplify → ALB → ECS → RDS
The Next.js portal calls /api/v1 through the ALB. Users sign in with Entra ID SSO or a local account.
D
Integrator APIExternal → ALB → ECS /pub/v1
Read-only public API. A bearer token is issued from the portal and scoped to a single customer tenant.
E
NotificationsECS → SES / Teams / webhook
Alerts and daily digests. Each customer tenant configures its own recipients and channels.
F
SSO redirectBrowser ⇄ Entra ID ⇄ ECS callback
OIDC authorisation-code flow. The user is provisioned just in time on first sign-in.

Key principles

  • No inbound firewall changes at site. The Collector connects out over standard HTTPS 443, with no VPN and no port forwarding.
  • HMAC on every Collector call. Each Collector has its own secret, which is decrypted server-side. Rotation is done by re-enrolment.
  • Row-level security in PostgreSQL. Tenant isolation is enforced in the database as well as in application code, giving defence in depth.
  • Secrets stay in AWS Secrets Manager. They are injected into the task at boot and are never stored in code or images.
  • UK-hosted exclusively. All customer data, including backups and snapshots, stays in AWS eu-west-2 (London). There is no cross-region replication.
  • Infrastructure as code. Every environment is defined in Terraform and can be rebuilt from source.
  • Offline-aware status. Collector heartbeats are tracked. If a Collector goes silent, its devices show Collector offline rather than a stale status.
